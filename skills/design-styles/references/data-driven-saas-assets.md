# Data-Driven SaaS Images & Graphic Assets Guide 2026

> A comprehensive, brand-neutral reference for product screenshots, interactive demos, workflow graphics, charts, diagrams, icons, borders, separators, customer proof, video, motion, 3D, and responsive visual production for SaaS websites.
>
> Use this document together with `data-driven-saas-web-design-system-2026.md`.

---

## 1. Purpose

Visual assets on a SaaS website must make the product easier to evaluate.

They should help users understand:

- what the software looks like;
- how a workflow functions;
- where value is created;
- how data moves;
- what output is produced;
- what is automated;
- what remains under human control;
- what proof supports the claims;
- how the product fits into a wider system.

A visual asset that merely makes the page look technological is not sufficient.

---

## 2. Asset hierarchy

Classify every asset as:

### Product evidence

- screenshot;
- interface recording;
- interactive demo;
- sample output;
- real report;
- workflow state;
- integration configuration.

### Customer or outcome evidence

- case-study image;
- customer quotation;
- metric;
- result chart;
- workflow comparison.

### Explanation

- diagram;
- process flow;
- architecture;
- data visualization;
- integration map;
- AI-control model;
- pricing graphic.

### Navigation

- icon;
- arrow;
- category marker;
- demo control;
- product-state symbol.

### Atmosphere

- gradient;
- abstract geometry;
- background illustration;
- texture;
- decorative 3D;
- ambient motion.

Priority:

```text
Product evidence > customer evidence > explanation > navigation > atmosphere
```

---

## 3. Visual direction

Suitable visual directions include:

- product-first;
- workflow editorial;
- data-led;
- technical enterprise;
- human productivity;
- developer-focused;
- security-led;
- AI with human control;
- industry-contextual.

Choose one primary direction.

Example:

```text
Primary: Product-first workflow visualization
Supporting: Technical diagrams and customer-result charts
Avoid: Generic AI mesh, floating UI cards, decorative 3D
```

---

## 4. Product screenshot strategy

A screenshot should show one useful product state.

Potential screenshot roles:

- hero overview;
- workflow step;
- feature detail;
- output;
- collaboration;
- settings;
- audit;
- mobile product;
- integration;
- analytics.

Do not show a complete dense dashboard at a size where nothing is readable.

Create separate screenshots for different messages.

---

## 5. Screenshot authenticity

Use:

- current product version;
- real component structure;
- realistic data;
- accurate labels;
- real permissions;
- plausible dates and states;
- actual supported workflow.

Do not:

- invent functionality;
- combine several screens into a fake interface;
- hide important limitations;
- create impossible metrics;
- show internal customer data;
- imply unreleased features are available.

Label conceptual, beta, or planned UI clearly.

---

## 6. Realistic sample data

Sample data should be:

- fictional or approved;
- internally consistent;
- realistic;
- safe;
- culturally appropriate;
- representative of the workflow.

Define:

- names;
- dates;
- units;
- locations;
- currencies;
- statuses;
- totals;
- relationships.

Avoid lorem ipsum, random percentages, generic `John Doe`, and impossible combinations.

Do not use real customer data without explicit approval and anonymization review.

---

## 7. Sensitive data review

Before publishing screenshots, inspect for:

- personal data;
- email;
- address;
- account identifiers;
- access tokens;
- API keys;
- internal URLs;
- customer names;
- financial data;
- health data;
- employee data;
- location;
- documents;
- audit history;
- browser bookmarks or notifications.

Use prepared demo workspaces rather than blurring many fields.

Blur can still reveal structure and may look unprofessional.

---

## 8. Screenshot composition

Define:

```text
Primary focal area
Context required
Crop
Annotation
Scale
Background
Device frame
Desktop/mobile role
Alt-text intent
```

Keep enough application chrome to establish context when needed.

Crop aggressively when only one detail matters.

Do not use extreme perspective transforms.

---

## 9. Screenshot readability

Ensure:

- meaningful text remains legible;
- UI scale is realistic;
- labels are not too small;
- important state is visible;
- contrast survives compression;
- screenshots remain useful on mobile.

Possible treatments:

- focused crop;
- zoomed detail;
- callout;
- side-by-side sequence;
- magnified inset;
- short interface recording.

Do not solve unreadable screenshots by placing them inside a larger decorative browser frame.

---

## 10. Browser and device frames

Use frames sparingly.

Suitable:

- simple browser header;
- subtle desktop window;
- mobile device outline;
- no frame for close crops.

Rules:

- keep frames subordinate;
- do not imitate a specific operating system inaccurately;
- avoid thick hardware mockups;
- do not use a device frame when the software is platform-independent;
- maintain accessible contrast.

---

## 11. Interface annotations

Annotations may explain:

- feature;
- workflow;
- data;
- control;
- change;
- AI source;
- approval;
- output.

Define one annotation system:

```text
Number or marker
Connector
Label
Description
Color
Position
Mobile behavior
```

Avoid crossing connectors and covering important UI.

Provide the same explanation in live text.

---

## 12. Product walkthrough sequences

A sequence should show:

```text
1. Starting state
2. Input or trigger
3. Product action
4. Human review
5. Output
6. Result
```

Use consistent viewport, data, and visual treatment.

Avoid disconnected feature slides.

---

## 13. Interactive demo assets

Interactive demos may use:

- screenshot hotspots;
- HTML prototype;
- embedded product;
- sandbox;
- guided click-through;
- video plus controls.

Requirements:

- explicit start;
- reset;
- progress;
- clear simulation status;
- keyboard alternative;
- mobile fallback;
- no forced lead form before value;
- accessible transcript or step list;
- realistic data.

Do not create deceptive interactions that appear to be the real product when they are not.

---

## 14. Demo loading and fallback

Provide:

- poster or static preview;
- loading state;
- failure message;
- retry;
- open full demo;
- step list;
- low-bandwidth alternative.

Do not leave an empty black or white embed when a third-party demo provider fails.

---

## 15. Interface recordings

Short recordings may demonstrate:

- automation;
- state change;
- collaboration;
- drag and drop;
- report generation;
- review;
- integration setup.

Rules:

- keep duration focused;
- crop to workflow;
- use readable cursor movement;
- avoid frantic movement;
- provide pause;
- provide captions or descriptive text;
- provide reduced-motion alternative;
- do not loop long sequences continuously near reading content.

Use video rather than GIF for longer sequences.

---

## 16. Product video

A product overview should explain:

- problem;
- workflow;
- output;
- outcome;
- next step.

Requirements:

- poster image;
- captions;
- transcript;
- no autoplay audio;
- product version review;
- realistic data;
- no unverified claim;
- mobile resolution;
- clear controls.

Avoid generic animated explainer videos that show little real product.

---

## 17. Workflow diagrams

A workflow diagram should identify:

- actor;
- input;
- action;
- system;
- automation;
- review;
- output;
- destination.

Use consistent node types.

Example roles:

```text
User
Product
External system
Data store
AI model
Human approval
Output
```

Do not use “AI” as a magical center node with unexplained arrows.

---

## 18. AI-system diagrams

For AI features, diagrams may show:

- source data;
- retrieval;
- model;
- tools;
- permissions;
- human review;
- output;
- storage;
- audit;
- external action.

Clearly distinguish:

- data flow;
- decision;
- recommendation;
- generation;
- agent action.

Show boundaries and stop points.

Do not disclose sensitive architecture details that create security risk.

---

## 19. Integration diagrams

Integration graphics should explain:

- connected system;
- direction;
- data type;
- trigger;
- action;
- authentication;
- frequency;
- ownership.

A logo grid alone does not explain integration.

Use official logos with permission and current brand assets.

Distinguish native, partner, API, automation platform, and planned integrations.

---

## 20. Architecture diagrams

Architecture visuals may support:

- enterprise evaluation;
- security review;
- deployment;
- data residency;
- API explanation;
- technical documentation.

Define node and connector semantics.

Provide a simplified marketing-level version and a detailed technical version where appropriate.

Do not imply a security guarantee through decorative shields or clouds.

---

## 21. Data visualization

Charts may communicate:

- customer result;
- usage;
- performance;
- workflow reduction;
- benchmark;
- reliability;
- growth;
- product output;
- sample analysis.

Every chart needs:

- question;
- value;
- unit;
- period;
- source;
- scope;
- comparison;
- accessible alternative.

Do not invent customer-result charts.

---

## 22. Chart selection

| Question | Recommended format |
|---|---|
| Exact value | KPI or table |
| Category comparison | Bar |
| Change over time | Line |
| Distribution | Histogram or box plot |
| Relationship | Scatter |
| Part-to-whole | Stacked bar; pie only for few categories |
| Workflow change | Before/after or sequence |
| Geographic result | Map only when location matters |
| Product sample output | Real chart matching the product |

Avoid 3D charts and decorative gauges.

---

## 23. Product charts versus marketing charts

A product chart should match the actual product design and capabilities.

A marketing chart may use simplified styling, but must preserve:

- accurate data;
- honest axes;
- relevant labels;
- product relationship.

Do not show a marketing visualization that the product cannot generate if the page implies it can.

---

## 24. Metrics and proof graphics

A metric block should include:

```text
Metric name
Value
Unit
Period
Scope
Comparison
Source
Context
```

Avoid large numbers detached from the evidence.

Customer-result graphics should link to a case study or methodology where appropriate.

---

## 25. Before-and-after workflow graphics

Show:

- previous tools or steps;
- new product workflow;
- removed work;
- retained human controls;
- resulting output.

Use honest comparisons.

Do not exaggerate the “before” state with intentionally chaotic graphics.

---

## 26. ROI calculator graphics

Visuals may include:

- input fields;
- assumptions;
- breakdown;
- result range;
- time horizon;
- sensitivity.

Keep charts readable and editable.

Label estimates.

Do not create a visually certain single result from uncertain inputs.

---

## 27. Pricing graphics

Pricing assets may explain:

- seat;
- usage;
- credits;
- storage;
- requests;
- automation runs;
- outcomes;
- add-ons.

Use examples:

```text
10 users
20,000 monthly records
500 AI actions
Estimated monthly total
```

Explain reset, rollover, overage, and measurement.

Avoid decorative credit tokens that make cost harder to understand.

---

## 28. Customer logos

Use only approved assets.

Rules:

- preserve proportions;
- maintain equal visual weight;
- do not recolor without permission;
- group with clear context;
- link to case evidence where possible;
- avoid implying endorsement beyond the actual relationship.

Do not create a giant logo wall as the only proof.

---

## 29. Testimonials and portraits

A testimonial should include:

- person;
- role;
- organization;
- specific context;
- result or observation;
- permission.

Use real portraiture where approved.

Do not generate customer portraits.

Do not use stock people beside real testimonials.

---

## 30. Industry photography

Photography can establish customer context:

- warehouse;
- office;
- clinic;
- field operation;
- manufacturing;
- retail;
- finance;
- support team.

Use specific, credible imagery.

Do not use industry photography to replace product proof.

Never imply stock subjects are customers.

---

## 31. Human-product relationships

Show people:

- using;
- reviewing;
- collaborating;
- making decisions;
- acting on output.

Avoid people pointing at fake holograms or smiling at blank laptop screens.

Keep product UI visible when it is the point.

---

## 32. Illustration

Suitable illustration styles:

- geometric editorial;
- technical line;
- data-informed;
- product-system;
- restrained 3D;
- human workflow;
- abstract brand illustration.

Define:

```text
Stroke
Fill
Palette
Perspective
Depth
Texture
Human proportions
Product relationship
Detail level
```

Do not use generic SaaS vector scenes.

---

## 33. 3D assets

3D may be used for:

- infrastructure;
- abstract data objects;
- product metaphor;
- developer technology;
- campaign identity.

It should not replace screenshots.

Requirements:

- clear purpose;
- limited material palette;
- optimized model;
- static fallback;
- reduced motion;
- mobile alternative;
- no fake interface content.

Avoid generic floating glass spheres, chrome blobs, and abstract cubes unless they have a specific brand meaning.

---

## 34. AI visual language

Do not represent AI only through:

- glowing brain;
- robot;
- magic sparkle;
- neural mesh;
- gradient sphere;
- hologram.

Better visual models may show:

- source;
- transformation;
- recommendation;
- human review;
- confidence;
- action;
- audit;
- boundary.

Use visual language that explains the product's actual AI behavior.

---

## 35. Icons

Define one functional icon family:

```text
Grid: 20, 24, or 32
Stroke
Fill
Caps
Joins
Corner
Optical size
Minimum size
```

Icon categories may include:

- product capability;
- workflow action;
- integration;
- security;
- data type;
- status;
- developer resource.

Avoid vague metaphors such as rocket for growth or sparkle for every AI feature.

Use labels for unfamiliar symbols.

---

## 36. Integration and brand icons

Use official integration marks where required.

Maintain:

- current asset;
- safe area;
- proportions;
- color rules;
- light/dark version;
- permission.

Do not redraw logos into a common icon style.

Custom category icons should not imitate third-party logos.

---

## 37. Borders and frames

Suitable systems include:

- product-window border;
- subtle panel rule;
- strong data frame;
- focus outline;
- accent edge;
- code block frame;
- chart plot boundary.

Use one main border language.

Avoid several layers of rounded frames around screenshots.

---

## 38. Separators

Suitable separators:

- whitespace;
- thin rule;
- section index;
- workflow connector;
- product-state bar;
- small color transition;
- code-like label.

Use separators for grouping and sequence.

Do not add abstract waves between every section.

---

## 39. Arrows and connectors

Define separate meanings for:

- workflow;
- data flow;
- navigation;
- external link;
- automation;
- approval;
- bidirectional synchronization.

Use consistent heads, weights, line styles, and labels.

Avoid arrows that point to decorative cards without explaining a relationship.

---

## 40. Patterns and texture

Suitable patterns:

- subtle grid;
- data points;
- code-derived motif;
- interface rhythm;
- integration lines;
- restrained grain.

Keep them subordinate.

Avoid visual noise behind screenshots, code, and body text.

---

## 41. Code assets

Code snippets should use:

- correct syntax;
- realistic example;
- language label;
- copy button;
- line wrapping or horizontal scroll;
- accessible contrast;
- explanation;
- secure placeholder values.

Do not publish real secrets or unsafe sample patterns.

Do not use screenshots of code when live text is practical.

---

## 42. Security graphics

Security visuals may explain:

- permission;
- encryption;
- deployment;
- isolation;
- audit;
- data flow;
- residency;
- retention.

Avoid generic shield icons as the entire trust story.

Use verified content and security-owner review.

Do not visualize a certification beyond its actual scope.

---

## 43. Badges and labels

Badges may indicate:

- beta;
- new;
- plan;
- availability;
- integration type;
- certification;
- status;
- AI-generated output.

Use concise labels.

Do not turn every metadata item into a pill.

Do not invent “enterprise-ready,” “secure,” or certification-style badges.

---

## 44. Motion design

Motion should show:

- product response;
- workflow progression;
- automation;
- collaboration;
- data update;
- state transition;
- approval.

Define:

```text
Purpose
Trigger
Duration
Easing
Loop
Pause
Reduced-motion alternative
Mobile version
```

Avoid constant movement near reading content.

---

## 45. Loading and status visuals

When showing product behavior, include realistic states:

- loading;
- empty;
- success;
- warning;
- error;
- partial;
- offline;
- stale;
- permission denied;
- human review required.

Do not present only ideal success states.

Product credibility increases when exception handling is visible.

---

## 46. Social and campaign assets

Prepare explicit compositions for:

- 1:1;
- 4:5;
- 9:16;
- 1.91:1.

Use:

- clear product crop;
- one message;
- specific outcome;
- safe text area;
- brand identifier;
- relevant proof.

Do not shrink an entire dashboard into a social preview.

## 47. Responsive visual delivery

Use responsive crops and sizes.

```html
<picture>
  <source
    media="(max-width: 48rem)"
    type="image/avif"
    srcset="/media/product-mobile-640.avif 640w,
            /media/product-mobile-960.avif 960w"
    sizes="100vw"
  />
  <source
    type="image/avif"
    srcset="/media/product-960.avif 960w,
            /media/product-1440.avif 1440w"
    sizes="(min-width: 90rem) 90rem, 100vw"
  />
  <img
    src="/media/product-1440.webp"
    width="1440"
    height="960"
    alt="Specific product screenshot description"
    loading="lazy"
    decoding="async"
  />
</picture>
```

Screenshots containing fine UI text may require WebP/PNG testing to avoid compression damage.

---

## 48. File formats

### AVIF / WebP

Use for photography and complex marketing visuals.

### PNG

Use when product screenshots or transparent raster UI require lossless detail.

### SVG

Use for icons, diagrams, charts, logos, borders, patterns, and line illustration.

### WebM / MP4

Use for interface recordings and product video.

### HTML

Prefer for interactive demos, code, accessible tables, and live product simulations.

Do not turn an interactive explanation into a GIF when a better format exists.

---

## 49. Accessibility

Classify assets:

```text
Informative
Functional
Decorative
Complex
Interactive
Timed media
Product evidence
```

Provide:

- alt text;
- detailed description;
- accessible demo alternative;
- captions;
- transcript;
- table;
- keyboard controls;
- visible focus;
- reduced motion;
- pause/stop;
- meaningful source and version.

Product screenshots need alt text that describes the relevant workflow or output, not every visible control.

---

## 50. Rights and governance

Record:

- product version;
- screenshot date;
- workspace source;
- data owner;
- customer approval;
- person consent;
- integration-logo permission;
- photographer;
- license;
- metric source;
- AI or conceptual status;
- review date.

Create a review cycle for outdated product visuals.

---

## 51. AI-generated imagery

AI may support:

- abstract brand illustration;
- conceptual campaign imagery;
- early visual exploration;
- clearly fictional scenes.

It must not be presented as:

- real customer;
- real employee;
- real product UI;
- real result;
- real industry deployment;
- real security architecture;
- real testimonial.

Generated text and interface details are unreliable. Build exact product UI and wording with controlled tools.

---

## 52. AI-generation template

```text
Clearly illustrative SaaS marketing visual, not a real product screenshot.
Concept: [specific product capability or workflow].
Visual model: [data flow, human review, integration, automation].
Composition: one clear focal relationship, negative space on [side].
Style: [geometric editorial / restrained technical / brand-specific 3D].
Palette: [defined limited palette].
Page role: [hero support / section transition / social].
Exclude: generated interface text, fake dashboard, logos, customer names,
generic AI brain, random neural mesh, floating glass cards, illegible labels.
Aspect ratio: [ratio].
```

Use real product assets for product proof.

## 54. Anti-patterns

Avoid:

- fictional product screenshots;
- lorem ipsum data;
- unreadable full dashboards;
- excessive browser/device frames;
- floating UI cards with no workflow;
- generic AI brain or mesh;
- fake charts;
- anonymous metrics;
- stock people beside customer quotes;
- unapproved customer logos;
- integrations shown only as logo decoration;
- fake security shields;
- generated code screenshots;
- excessive glassmorphism;
- motion showing impossible behavior;
- ideal states only;
- product video without captions;
- desktop screenshot simply shrunk on mobile.

---

## 55. AI-agent instructions

An AI agent must:

1. classify every asset by evaluation purpose;
2. use current verified product states;
3. create realistic safe sample data;
4. protect sensitive information;
5. define screenshot, sequence, and demo strategy;
6. define workflow and AI-control diagrams;
7. define chart source and context;
8. define icon, border, separator, and connector systems;
9. define responsive mobile visuals;
10. provide accessible alternatives;
11. record version, rights, and approvals;
12. distinguish conceptual from real UI;
13. avoid generic SaaS visual clichés;
14. ensure product evidence remains dominant.

## 58. Final rule

Data-Driven SaaS visual assets must prove the product, explain the workflow, demonstrate outcomes, and reduce buyer uncertainty. Real interface evidence and verified data take priority over abstract technology decoration.
