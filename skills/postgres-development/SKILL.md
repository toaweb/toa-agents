# PostgreSQL development

Senior PostgreSQL specialist. Target PostgreSQL 18 (works with 17+) with
SQLAlchemy 2.0 async and Alembic. Verify the server version per project — a few
capabilities below (native `uuidv7()`) are Postgres 18+.

## Core principles

**Least privilege.** The application connects as a dedicated role with DML only
(SELECT/INSERT/UPDATE/DELETE). It never connects as the Postgres superuser.
Schema changes (DDL) run as the migration/owner role, not the app role.

**Separate DDL and DML roles.** Alembic runs as the owner/superuser role and
performs DDL; the app runs as `<app>_app` and performs DML only. The app role
must have a password set explicitly — creating the role does not set one, and
scram-sha-256 auth fails without it.

**Never expose the database on an edge/public network.** Keep Postgres on an
internal network only; nothing routable from the internet.

**Migrations are append-only.** Always review an autogenerated migration before
running it. Never edit a migration that has already been applied — write a new one.

**Design for the query.** Index every foreign key and every column used in
frequent WHERE/JOIN/ORDER BY. Use `EXPLAIN ANALYZE` on slow queries rather than
guessing.

**Consistent, typed models.** SQLAlchemy 2.0 `Mapped[T]` + `mapped_column`, a
`TimestampMixin` on every table, and the naming conventions in the reference.

## Anti-patterns — never produce these

- Connecting the app as the Postgres superuser, or granting it DDL rights.
- An app role created without a password (breaks scram-sha-256 login).
- The database reachable on a public/edge network.
- Old SQLAlchemy `Column(...)` attribute style — use `Mapped[T]`.
- Editing an already-applied migration instead of adding a new one.
- Applying an autogenerated migration without reading it first.
- Unindexed foreign keys or hot WHERE columns.
- Tables without `created_at` / `updated_at`.
- asyncpg behind PgBouncer transaction-pooling mode without mitigation — its
  server-side prepared statements break there.

## Workflow

1. Confirm the Postgres version and whether the app/migration roles exist with
   the right privileges and a password.
   - **Before relying on any Postgres 18 feature, fetch
     https://www.postgresql.org/docs/18/release-18.html and confirm it against
     the release notes** rather than from memory — the target server may be older.
2. **Before writing models, migrations, or role setup**, read
   `references/patterns.md` — naming conventions, ID strategy (IDENTITY vs
   `uuidv7()`), the SQLAlchemy 2.0 model shape, the app-role `init.sql`, the
   Alembic commands, and the driver/PgBouncer note.
   - **Before using `uuidv7()` or choosing an ID strategy, fetch
     https://www.postgresql.org/docs/18/functions-uuid.html and confirm the
     function and its signature on the target server. It is Postgres 18+** — do
     not assume it on older servers.
3. For any model change: autogenerate a migration, **read it**, then apply.
4. Index foreign keys and frequent filter columns; `EXPLAIN ANALYZE` slow queries.
5. Put `TimestampMixin` on every model.
