# Agent Skills

A collection of **brand-neutral [Agent Skills](https://docs.claude.com/en/docs/claude-code/skills)**
for web and backend development. Each skill packages the role, principles,
anti-patterns and workflow for one domain (Astro, FastAPI, Hugo, Nuxt, Postgres,
Tailwind, copy-editing, art direction, …), with the heavy detail in reference
files the skill tells the agent to read on demand.

**Neutral by design.** No skill contains brand values — no specific colours,
fonts, logos, hostnames, private paths, or organisation-specific tooling. A
skill describes *how* to work in its domain; it reads the concrete brand values
from the project it is used in (see [Bringing your brand](#bringing-your-brand)).

## Repository layout

```
skills/
  <skill-name>/
    SKILL.md              frontmatter + role, principles, anti-patterns, workflow
    references/*.md        heavy detail (patterns, checklists, examples)
    assets/                optional (e.g. token CSS)
    scripts/               optional (e.g. a compliance check)
  design-styles/          the style catalogue: one reference file per named style
agents/
  coder.md                generic implementation agent (full write access)
  researcher.md           verification agent (read + fetch, no source edits)
  auditor.md              review agent (strictly read-only)
scripts/
  validate.py             structural + neutrality validator (no dependencies)
  install.sh              symlink skills + agents into ~/.claude/
  neutrality-terms.example.txt   format docs for the private term list
  neutrality-terms.local.txt     YOUR terms — gitignored, never committed
```

Each `SKILL.md` stays lean (under ~5000 tokens) and points at its `references/`
files as instructions ("read X before doing Y"), so the detail loads only when
needed.

## Installing

Skills are consumed by symlinking them into your Claude skills directory
(`~/.claude/skills/`). Use the provided script:

```bash
scripts/install.sh            # symlink every skill into ~/.claude/skills/
scripts/install.sh --dry-run  # show what would happen, change nothing
```

The script uses absolute paths (the repo can live anywhere), is idempotent (safe
to re-run), and refuses to overwrite anything that is not already a symlink into
this repo — it warns instead. It also links `agents/*.md` into
`~/.claude/agents/` (override with `CLAUDE_AGENTS_DIR`). See
`scripts/install.sh` for details.

## Agents

Three generic agents — that is deliberate. **A skill is knowledge; an agent is
an execution context.** Domain expertise lives in the skills so it loads
on demand in any context; the agents differ only in *permissions*:

| Agent | Access | Job |
|---|---|---|
| `coder` | full read/write, runs builds & tests | implements changes |
| `researcher` | read + fetch, no source edits | verifies versions/APIs against primary sources |
| `auditor` | strictly read-only | reviews against the standards the skills define |

Every agent's first mandatory step is the **skills lookup**: find and read the
matching `skills/<name>/SKILL.md` before doing domain work. That line is what
makes the setup portable — Claude Code auto-triggers skills, other clients
(Codex, OpenCode, …) do not, but the explicit instruction works everywhere.
The agent files are canonical, client-neutral markdown; point each client at
them (or add a translation step in `install.sh`) so this repo stays the single
place anything is edited. `validate.py` fails any agent that drops the lookup
instruction.

Add a fourth agent only when a task genuinely needs different *permissions or
tools* (e.g. a creative agent with image-generation tools) — never for
knowledge; knowledge goes in a skill.

## Design styles

`skills/design-styles/` is the catalogue of named styles (brutalism, retro
terminal, …): a router `SKILL.md` plus one complete, versioned definition per
style under `references/`. When a user names a style, the agent reads that
definition in full and designs to it — never from memory. Styles are
brand-neutral method; the project's brand values are applied on top, from the
project's own brand source. Styles big enough to carry their own scripts and
assets (like `modern-corporate-design`) live as full skills, and the catalogue
points to them.

Adding a style = one reference file + one row in the catalogue table.

## Adding a new skill

1. Create a directory under `skills/` named in `lowercase-hyphens`
   (max 64 chars). The directory name **must** equal the skill's `name`.

2. Add `SKILL.md` with YAML frontmatter and a body:

   ```markdown
   ---
   name: my-skill
   description: What it does AND when to use it AND what it is not for. This is
     the trigger the agent matches on — spend words on it (max 1024 chars).
   ---

   # My skill

   Role, principles, anti-patterns, workflow. Keep this under ~5000 tokens and
   point at reference files as instructions, e.g. "before doing X, read
   `references/patterns.md`".
   ```

3. Put the heavy material — patterns, checklists, long examples — in
   `references/*.md`, and **mention each reference file from `SKILL.md`** so the
   agent knows to read it. A reference that nothing points to is dead weight;
   the validator flags it.

4. Keep it neutral: no brand colours, fonts, logos, hostnames, private paths, or
   organisation-specific tooling. Read those from the project instead.

5. Validate before committing:

   ```bash
   python3 scripts/validate.py
   ```

   It checks frontmatter, the name/directory match, description length, body
   size, that every referenced file exists, and flags any brand/personal-path
   markers for review. It exits non-zero on any hard failure.

### Requirements enforced by the validator

| Check | Level |
|---|---|
| `SKILL.md` exists with valid `--- frontmatter ---` | FAIL |
| `name` and `description` present | FAIL |
| `name` equals the directory name | FAIL |
| `name` is lowercase-hyphens, ≤ 64 chars | FAIL |
| `description` ≤ 1024 chars | FAIL |
| Every referenced `references/`, `assets/`, `scripts/` file exists | FAIL |
| `description` ≥ ~15 words (states WHAT and WHEN) | WARN |
| Body ≤ ~4000 tokens (ceiling ~5000) | WARN |
| Reference file present but never mentioned | WARN |
| Brand / personal-path / tooling markers — scans **every** text file in the skill dir (frontmatter, `references/`, `assets/`, `scripts/`) | WARN (manual review) |
| `agents/*.md`: frontmatter valid, name matches filename | FAIL |
| `agents/*.md`: contains the mandatory `skills/` lookup instruction | FAIL |

### The private neutrality term list

The validator's brand markers load from `scripts/neutrality-terms.local.txt`
(**gitignored**) — one term per line; plain words match whole-word, terms with
non-word characters match as substrings, and hex values (with or without `#`)
match as brand colors. The list is your private vocabulary — usernames,
hostnames, brand hexes — which is exactly why it must never be committed to a
public repo: publishing the detector's dictionary defeats its purpose. Copy
`scripts/neutrality-terms.example.txt` to get started. Without the local file
the validator warns and checks only generic fallbacks.

## Bringing your brand

These skills are deliberately **brand-neutral**. They describe method, not
identity. When a skill needs a concrete value — a colour, a font, a logo, a
design-token file — it is written to **read that from the project it runs in**,
for example a `brand.json`, a `theme/tokens/` directory, a design tokens export,
or a path you point it at. If no such source exists and the work genuinely needs
brand values, the skill asks rather than inventing them.

This keeps one copy of each skill usable across many projects: the method is
shared, the identity stays in each project.

## A note on technical references

The framework/library specifics in the development skills (version numbers, API
signatures, config keys, "the framework does X automatically") were **verified
against official documentation at migration time**, and each such skill records
that in a short *source note*. Software moves; treat these as *current as of
migration*, not permanent truth. **Re-verify versions and API details per
project**, especially for fast-moving, pre-1.0 dependencies. The non-technical
skills (copy-editing, art direction) rest on stable craft rather than versioned
APIs.
